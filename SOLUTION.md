## 1. Project Title

**AI-Assisted Analysis of Student Learning Progress in Vocational IT Education**

A small, reproducible ML project that explores how a teacher in a vocational IT programme could be supported — not replaced — by a baseline classifier that highlights students who may need additional help.

## 2. Motivation

I teach special disciplines in a vocational IT context (среднее профессиональное образование) at **GAPOU "YAKSIT"** in Yakutsk. My current teaching load includes professional-cycle modules **MDK 01.01** (Operating systems), **MDK 01.02** (Databases), and **MDK 01.04** (Operation of automated systems in a protected configuration). These subjects sit at the intersection of hands-on systems work, data literacy and information security — which is why I care about both **early warning signals** (attendance, lab practice, project milestones) and **explainable** analytics rather than opaque scores.

In my day-to-day work I see two recurring situations:

* A few students start to fall behind early in the course, but the signal is hard to see until grades drop visibly.
* When the teacher finally notices, the room for meaningful intervention has already shrunk.

I want to understand how machine learning and modern AI tools can help me, as an educator, **notice these early signals sooner** and have a more informed conversation with the student.

This project is not an attempt to "automate teaching". Pedagogical decisions must stay with the teacher. The role I see for ML is much more modest: a calm second opinion that surfaces patterns from many features at once and offers them to the teacher as input — never as a verdict.

This project is also a way to demonstrate the skills and the mindset I would bring to SMILES-2026: applied data analysis, a focus on interpretability, and an explicit awareness of the ethical context of using AI in education.

## 3. Problem Statement

> Given a small set of learning indicators collected during a vocational IT course, can a simple ML model produce a useful **risk signal** that helps the teacher decide where to look first?

Formally, this is a multi-class classification task:

* **Input (X):** seven features describing each student (attendance, coursework scores, practice hours, AI-tool usage, prior IT background).
* **Output (y):** `risk_level ∈ {low, medium, high}`.
* **Constraint:** the model must be **interpretable**, so that the teacher can see *why* a particular student is flagged.

The cost of a false negative (a struggling student that the model misses) is higher than the cost of a false positive (a student that the model flags but who turns out to be fine). This shapes how I evaluate the model later.

## 4. Dataset

The dataset is **fully synthetic** and is generated by [`src/generate_data.py`](src/generate_data.py). It contains **no personal information** and is not derived from real students. The script is seeded (`random_state = 42`), so the data is reproducible.

| Field                       | Type        | Description                                                  |
| --------------------------- | ----------- | ------------------------------------------------------------ |
| `student_id`                | string      | Synthetic identifier (`S0001`, `S0002`, …)                   |
| `attendance_rate`           | float [0,1] | Share of classes attended                                    |
| `assignment_score`          | float 0–100 | Average homework / assignment score                          |
| `quiz_score`                | float 0–100 | Average quiz score                                           |
| `project_score`             | float 0–100 | Score on the practical project                               |
| `practice_hours`            | float       | Hours spent on self-study practice                           |
| `ai_tool_usage_frequency`   | int 0–5     | Self-reported frequency of using AI tools while studying     |
| `previous_it_experience`    | int 0/1     | Whether the student had prior IT experience                  |
| `final_result`              | float 0–100 | Numeric final result (used to define `risk_level`)           |
| `risk_level`                | category    | `low` / `medium` / `high` (target variable)                  |

The generator creates a latent "academic strength" score from `attendance_rate`, `practice_hours`, `previous_it_experience` and `ai_tool_usage_frequency`, then derives the three coursework scores from that latent score with independent gaussian noise. `final_result` is a weighted average of the coursework scores plus a small noise term, and `risk_level` is obtained by thresholding `final_result`.

By construction the data is **noisy but learnable**, and the class distribution is realistic for a vocational programme: low risk is the majority, medium is a meaningful minority, and high risk is a small but non-trivial group.

A typical run produces:

| risk_level | count |
| ---------- | ----- |
| low        | ~287  |
| medium     | ~252  |
| high       | ~61   |

(Exact counts depend on the seed and the dataset size.)

## 5. Methodology

The pipeline is intentionally short and easy to audit.

1. **Synthetic data generation** — `src/generate_data.py` produces `data/student_progress_sample.csv`.
2. **Preprocessing** — minimal: drop `student_id` and `final_result` from the feature matrix (`final_result` would leak the target). All features are numeric and tree-friendly, so no scaling is required.
3. **Exploratory data analysis** — distributions, group means by `risk_level`, and the correlation matrix are produced by `src/analyze_results.py` and reproduced in the notebook.
4. **Train / test split** — stratified 75% / 25%, `random_state = 42`.
5. **Model training** — `RandomForestClassifier` with `class_weight="balanced"`.
6. **Evaluation** — accuracy, macro precision / recall / F1, per-class metrics, confusion matrix, with an explicit focus on recall for the `high` class.
7. **Interpretability** — `feature_importances_` plus a written reading guide that maps the numbers back to the educational context.

All artifacts (`metrics.json`, `classification_report.txt`, `confusion_matrix.png`, `feature_importance.csv`, `feature_importance.png`, EDA plots and a `summary.md`) are written to [`results/`](results/).

## 6. Model

The baseline model is a **Random Forest classifier** (`scikit-learn`):

```text
RandomForestClassifier(
    n_estimators=300,
    min_samples_leaf=2,
    class_weight="balanced",
    random_state=42,
    n_jobs=-1,
)
```

Why Random Forest for a baseline:

* It handles **mixed-scale numeric features** without manual scaling.
* It works well on **small tabular datasets** — which is what real educational data usually is.
* `class_weight="balanced"` compensates for the underrepresented `high` class.
* It exposes `feature_importances_`, which gives a usable first-order explanation. For a project whose stated goal is "support the teacher, do not replace them", interpretability is more important than squeezing out one extra percent of accuracy.

A simple logistic regression was considered as an even more interpretable alternative. It is a good complementary model to run in future iterations, but Random Forest is a more honest baseline for the non-linear relationships built into the synthetic data.

## 7. Evaluation

On a representative run (600 students, 75/25 stratified split, seed 42):

| Metric              | Value  |
| ------------------- | ------ |
| Accuracy            | ~0.83  |
| Precision (macro)   | ~0.86  |
| Recall (macro)      | ~0.79  |
| F1 (macro)          | ~0.82  |
| Recall on `high`    | ~0.67  |

The per-class classification report and the confusion matrix are stored in [`results/classification_report.txt`](results/classification_report.txt) and [`results/confusion_matrix.png`](results/confusion_matrix.png).

**Why recall on the `high` class matters most.** In this use-case a false negative — a student who is actually at high risk but the model labels as low or medium — means the teacher does not get an early-warning signal where it is needed most. A false positive — flagging a student who turns out to be fine — only triggers a check-in conversation, which is rarely harmful and is the kind of action a good teacher would do anyway. The asymmetry of these errors is the reason `class_weight="balanced"` is used and the reason `recall_high_risk` is reported as a headline metric.

The current baseline catches roughly two thirds of the high-risk students. This is consistent with a small synthetic dataset and an intentionally noisy generator; it is **not** a claim that real-world performance would be the same.

## 8. Explainability

`feature_importances_` (averaged Gini-impurity reduction) gives the following ranking on a representative run:

| Rank | Feature                   | Importance (≈) |
| ---- | ------------------------- | -------------- |
| 1    | `assignment_score`        | 0.27           |
| 2    | `project_score`           | 0.26           |
| 3    | `quiz_score`              | 0.20           |
| 4    | `attendance_rate`         | 0.11           |
| 5    | `practice_hours`          | 0.07           |
| 6    | `previous_it_experience`  | 0.05           |
| 7    | `ai_tool_usage_frequency` | 0.04           |

Two observations:

* The three coursework scores are the dominant signal. This is expected — they are direct proxies for current academic performance.
* `attendance_rate` and `practice_hours` are weaker individually but are the **earliest available** features in a course; in a real deployment they would be the most useful inputs for *early* warning.

Feature importance is a model-specific, non-causal measure. In future work I would add **SHAP** to obtain per-student explanations, which are much more useful when the teacher discusses results with a specific student.

## 9. Results and Discussion

What the project shows:

* A small, transparent ML pipeline can produce a usable risk signal on this type of educational tabular data.
* Coursework scores dominate, but behavioural features (`attendance_rate`, `practice_hours`) carry a real, earlier signal.
* The error pattern is reasonable: most mistakes are between adjacent classes (`low` ↔ `medium`, `medium` ↔ `high`), rather than between `low` and `high`.

What the project deliberately does **not** show:

* It does **not** prove that ML can predict real students' outcomes — the dataset is synthetic.
* It does **not** claim that the reported metrics generalise — they are tied to one seed and one generator.
* It does **not** suggest that a teacher should rely on this model in practice — it is a demonstration baseline.

A more honest framing of the result is:

> Even a simple, interpretable baseline can produce signals that **a teacher could meaningfully react to** — but only as a complement to, never as a replacement for, the teacher's own judgement.

## 10. Ethical Considerations

This is the part of the project that matters the most to me, both as an educator and as someone interested in responsible AI.

* **No personal data.** The dataset is synthetic. The repository contains no real student records of any kind.
* **Support, not replace.** A risk score is a hint, not a verdict. A teacher must remain the decision-maker for any action that affects a student (extra help, repeated coursework, etc.).
* **Avoid unfair labelling.** A model like this can quietly stigmatise students if its predictions are visible without context. Risk scores should not be shown to the student as a fixed label; if they are shared with the student, they should be framed as a conversation, not a diagnosis.
* **Human review.** Every action that follows from a model prediction should involve a human (the teacher, the curator, the educational psychologist where available).
* **Transparency and explainability.** Students and teachers should be able to see which features drove a particular prediction. This is one reason I chose a tree-based model with `feature_importances_` (and why I plan to add SHAP).
* **Bias.** A real version of this model would have to be audited for bias along axes such as gender, age, prior education and region. On synthetic data this audit is not meaningful, but the production version must include it.
* **Data minimisation.** Only collect the features that are actually needed. In a real deployment, I would prefer to start with the simplest possible feature set (e.g., attendance and a single coursework score) and add features only when their value is proven.
* **Opt-in / opt-out.** Students should be informed when such a tool is used in their programme.

## 12. Future Work

If I were to take this project further, the next steps would be, in order of priority:

1. **Replace synthetic data with real, anonymised educational data**, obtained through proper consent and ethical review. Nothing else in this project is more important than this step.
2. **Compare more ML models** (`LogisticRegression`, gradient boosting, calibrated classifiers) and report calibrated probabilities, not just labels.
3. **Add SHAP** for per-student, local explanations that are usable in a teacher–student conversation.
4. **Develop a small teacher dashboard** that surfaces signals and lets the teacher override them, with the override stored as a first-class data point.
5. **Integrate LLM-generated feedback carefully** — for example, summarising a student's recent activity in plain language — with strict guardrails and human review before anything reaches a student.
6. **Test the approach in a real vocational education context**, ideally as a pilot with a single discipline and a willing group of teachers and students.
